※Cromtechで検証中の別プロダクト「Keros」を作る中で考えたことです。

他人が書いたコードのバグを直すのは、自分のコードを直すより神経を使う。理由ははっきりしていて、「直したつもりが、関係ないところを壊す」からだ。仕様の意図が分からない、テストがない、その一行がなぜそう書いてあるのか誰も覚えていない。受託や保守で入ると、だいたいこの状態から始まる。

だから手を動かす前に、「今回どこまで触っていいか」を先に決めるようにしている。

## 1. まず再現する

再現できないバグは直さない。「カートがおかしい」だけのような曖昧なチケットは、まず再現条件を詰める。ここを飛ばして「たぶんここだろう」で直すと、直っていないのに直った気になる。一番危ない。

## 2. 関係するファイルと「理由」をセットで特定する

どのファイルが関係するか、だけでは足りない。「なぜ関係すると言えるか」まで言葉にする。

たとえば「商品を削除しても合計金額が更新されない」なら、
「合計は `Cart.tsx` の中で計算されている → でも `cart` が変わっても再計算される作りになっていない」
というふうに、症状から原因まで一本の線でつなぐ。ここが言えないうちは、まだ直す段階じゃない。

## 3. 「触る所」と「触らない所」を分ける

影響範囲は最小にする。今回のバグに関係ない箇所は、気になっても今回は触らない。「ついでにリファクタ」は、レビューを重くするし、バグ修正なのか改善なのか分からないPRを生む。別のPRに分けて出す。

## 4. 分からなければ、直さない

情報が足りないまま見当で直すくらいなら、「ここまでは分かった、ここが分からない」と書いて止める方がいい。間違ったたたき台は、レビューする人の時間まで奪う。

---

この「初動の範囲決め」は地味だけど、保守の質をほぼ決めていると思う。そしてたいてい、特定の人の頭の中にしかない。

最近はこの初動を半自動でやる仕組みを作っている。Backlogのバグチケットを受けて、リポジトリを調べ、「どのファイルがなぜ関係するか」を根拠つきでGitHubのDraft PRのたたき台にする。上の1〜4をそのまま道具にした感じだ。自動マージはしない。レビューやマージは今まで通り人が判断する。

実際に作った例をそのまま置いてあるので、動きが気になる人はどうぞ（登録不要）: https://keros.repocarta.jp/example
