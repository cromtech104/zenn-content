自分の書いたコードなら、バグの直し方はだいたい見当がつく。面倒なのは他人のコードのほうだ。受託でも保守でも、入った時点でテストはないし、ドキュメントは古いし、その一行がなぜそう書いてあるのか誰も覚えていない。そういう状態で「ここ直しといて」と渡される。

一番こわいのは、直した箇所じゃなくて、直したせいで別のところが動かなくなることだ。なので手を動かす前に、今回はどこまで触るかを先に決めるようにしている。

まず、再現できないバグは直さない。「カートがおかしいです」だけのチケットが来ても、自分の手元で同じ症状を出すところから始める。ここを飛ばして「たぶんこの辺だろう」で直すと、直っていないのに直った気になって、しばらくしてまた同じ報告が返ってくる。

再現できたら、原因を一行で言えるところまで持っていく。「どのファイルが怪しいか」ではなく「なぜそこが原因と言えるか」まで。合計金額が更新されないバグなら、`Cart.tsx` の中で合計を計算しているのに商品を消しても再計算が走っていない、くらいまで言葉にできて、やっと直していい。ここが説明できないうちは、まだ直す段階じゃないと思っている。

触る範囲は狭くする。今回のバグに関係ない場所は、どれだけ気になっても今回はいじらない。「ついでにここも直しておくか」をやると、レビューする人がこれはバグ修正なのか改善なのか分からなくなる。気になった箇所は別のチケットに書いて、別のPRで出す。

そして、分からなかったら直さない。無理に見当で直すくらいなら、「ここまでは追えた、ここから先が分からない」と書いて止めたほうがいい。中途半端なたたき台を渡されるのは、レビューする側からするとかなりつらい。時間を取られた挙句、結局最初から見ることになる。

書いてみると当たり前のことばかりだが、この最初の見極めが保守の当たり外れをだいたい決めている気がする。そしてこの見極めは、たいていチームの特定の誰かの頭の中にしかない。その人が忙しいと初動がまるごと止まる。

最近はこの初動の部分を半分くらい機械にやらせられないかと思って、仕組みを作っている。Backlogのバグチケットを拾って、リポジトリを調べて、どのファイルがなぜ関係しそうかを根拠つきでGitHubのDraft PRのたたき台にする、というものだ。ここに書いた見極めを、そのまま道具にしている。マージは人がやる。

動くものを置いてあるので、気になる人はどうぞ（登録はいらない）。
